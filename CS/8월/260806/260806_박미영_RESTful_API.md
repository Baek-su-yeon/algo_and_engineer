### 1. API란?

- Application Programming Interface의 약자
- 서로 다른 프로그램이 기능이나 데이터를 주고받을 수 있도록 정해놓은 인터페이스
- **프로그램과 프로그램이 소통하기 위해 정해놓은 요청 방식과 규칙**
- 클라이언트가 서버의 데이터베이스나 내부 기능에 직접 접근하면 보안과 괸리 측면에서 문제가 생길 수 있음.
⇒ 그래서 서버는 외부에서 사용할 수 있는 기능과 요청 방식을 API로 정해놓음.
- **클라이언트는 API를 통해 서버에 요청하고, 서버는 요청을 처리한 뒤 결과를 응답**

### 2. RESTful API란?

- API에도 여러 설계 방식이 있음.
- 그 중 웹에서 많이 사용하는 방식이 REST API
- REST 원칙을 잘 지킨 API를 RESTful API라고 함

- **REST (Representational State Transfer)**
    - **웹의 자원을 일정한 원칙에 따라 주고받도록 만든 아키텍쳐 스타일**
    - **서버의 데이터를 자원으로 보고, 자원의 위치를 URI로 나타내며, HTTP 메서드를 통해 자원을 처리하는 방식**
    - 예를 들어, 게시글 목록을 조회한다면 다음과 같이 표현
        
        ```python
        GET /posts
        ```
        
        - `/posts` : 게시글이라는 자원
        - `GET` : 게시글을 조회한다는 행위
    - **좀 더 자세한 설명**
        - **서버의 데이터를 자원으로 본다 ?**
            - 자원 : 클라이언트가 서버에 요청해서 조회하거나 변경할 수 있는 대상
            - 서버가 관리하는 회원, 게시글, 상품, 주문과 같은 데이터를 각각 하나의 자원으로 봄.
        - **자원의 형태**
            - 서버에 저장된 자원 자체가 클라이언트로 이동하는 것이 아니라, 자원을 JSON 같은 형태로 표현해서 전달함.
                
                ```python
                GET /posts/1
                ```
                
                ```json
                {
                  "id": 1,
                  "title": "RESTful API",
                  "content": "REST를 공부합니다."
                }
                ```
                
                - 실제 자원 : 서버나 데이터베이스에 저장된 게시글
                - 자원의 표현 : 클라이언트에게 전달된 JSON 데이터
            - **REST는 자원의 현재 상태를 JSON 등의 표현 형태로 주고받는 방식**
        - **URI (Uniform Resource Identifier)**
            - 인터넷에서 특정 자원을 구분하기 위한 식별자
            - 서버가 관리하는 게시글, 회원, 상품 같은 자원을 URI로 나타냄.
                
                ```python
                /posts
                /users
                /products
                ```
                
            - 예를 들어, 아래는 1번 게시글이라는 자원을 나타내는 URI
                
                ```python
                /posts/1
                ```
                
            - **URI 자체는 행동을 나타내지 않고, 어떤 대상을 다루는지를 나타냄.**
        - **URL vs URI**
            - URI : 자원을 식별하는 개념
            - URL : 자원의 위치까지 나타내는 URI
        - **HTTP 메서드**
            - 클라이언트가 서버의 자원에 대해 어떤 작업을 원하는지 나타내는 방식
            - **앞에서 URI가 자원을 나타냈다면, HTTP 메서드는 그 대상에 무엇을 할 것인가를 나타냄.**
            - 예시)
                
                ```python
                GET /posts/1
                ```
                
                - `/posts/1`  : 1번 게시글
                - `GET` : 조회
                - **1번 게시글을 조회해 달라는 요청**
            - URI만 적혀 있다면 그 자원으로 무엇을 하려는지 알 수 없음.
        - **주요 HTTP 메서드**
            - GET : 조회
            - POST : 새로운 자원 생성
            - PUT : 기존 자원을 전체 수정 또는 교체
            - PATCH : 기존 자원의 일부만 수정
            - DELETE : 자원 삭제
        - **HTTP 상태 코드**
            - 요청 처리 결과가 어떠한가
            
            | 상태 코드 | 의미 |
            | --- | --- |
            | 200 OK | 요청 성공 |
            | 201 Created | 자원 생성 성공 |
            | 204 No Content | 성공했지만 응답 본문 없음 |
            | 400 Bad Request | 잘못된 요청 |
            | 401 Unauthorized | 인증되지 않음 |
            | 403 Forbidden | 접근 권한 없음 |
            | 404 Not Found | 자원을 찾을 수 없음 |
            | 500 Internal Server Error | 서버 내부 오류 |
- **RESTful API**
    - **REST의 설계 원칙을 잘 지켜 만든 API**
- **RESTful 하지 않은 표현이란?**
    - 다음처럼 URI에 행동을 직접 넣을 수도 있음.
        
        ```python
        /getPosts
        /createPost
        /deletePost
        ```
        
    - 하지만 REST에서는 URI에는 자원만 나타내고, 행동은 HTTP 메서드로 구분하는 방식을 권장함.
        
        ```python
        GET /posts
        POST /posts
        DELETE /posts/1 
        ```
        

### 3. REST의 특징 (+웹에서 REST를 많이 사용하는 이유)

1. **클라이언트-서버 구조**
    - 클라이언트와 서버의 역할을 분리함.
    - 클라이언트 : 화면 표시, 사용자 입력
    - 서버 : 데이터 관리, 비즈니스 로직 처리
    - 예를 들어 상품 조회 서비스라면,
        - 클라이언트는 상품 목록을 화면에 보여줌
        - 서버는 상품 데이터를 조회해 전달함
        - ⇒ 역할이 분리되어 있기 때문에 클라이언트 화면이 바뀌어도 서버 기능을 그대로 사용할 수 있음.
    - **⇒ 화면과 서버를 독립적으로 개발하기 쉬움**
2. **무상태성 - Stateless**
    - 서버는 클라이언트의 이전 요청 상태를 기억하지 않음.
    - 각 요청에는 서버가 처리하는 데 필요한 정보가 모두 포함되어야 함.
    - 예를 들어 사용자의 인증이 필요한 요청이라면 매 요청마다 인증 정보를 함꼐 보내야 함.
        - 여기서 Stateless는 서버가 데이터를 저장하지 않는다는 뜻이 아님.
        - 이전 요청에 의존해서 다음 요청 처리 : 지양
        ⇒ 각 요청이 독립적
    - **⇒ 요청을 여러 서버에 나눠 처리하기 쉬워 확장에 유리함**
3. **캐시 가능성 - Cacheable**
    - 서버의 응답은 캐시할 수 있는지 명확하게 표시해야 함.
    - 성능과 응답 속도를 높일 수 있음.
    - **⇒ 응답 속도가 빨라지고 서버 부담이 줄어듦**
4. **일관된 인터페이스 - Uniform Interface**
    - 가장 핵심 특징
    - 클라이언트가 자원에 접근하는 방식을 일관되게 만듦.
    - **⇒ API의 규칙이 일관되어 이해하고 사용하기 쉬움**
5. **계층화 구조 - Layered System**
    - 클라이언트와 서버 사이에 여러 중간 계층이 존재할 수 있음.
    - 클라이언트는 중간에 게이트웨이나 프록시, 로드 밸런서가 있는지 알 필요 없이 API만 호출하면 됨.
    - 각 계층은 인증, 보안, 트래픽 분산 등의 역할을 담당할 수 있음.
    - **⇒ 게이트웨이, 로드 밸런서, 보안 계층 등을 유연하게 추가할 수 있음**
6. **주문형 코드 - Code on Demand**
    - 필요한 경우 서버가 클라이언트에 실행 가능한 코드를 전달할 수 있음.

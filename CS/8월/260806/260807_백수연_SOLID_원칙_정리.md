# SOLID 원칙

> 직무면접 대비 CS 용어 정리 노트

객체지향 설계에서 유지보수성과 확장성을 높이기 위한 다섯 가지 핵심 원칙. 서로 독립된 규칙이 아니라 하나의 설계 철학을 이루며 맞물려 있다.

---

## 1. SRP (단일 책임 원칙, Single Responsibility Principle)

**클래스는 하나의 책임만 가져야 한다.** 정확히는 "메서드가 하나여야 한다"가 아니라, **클래스가 바뀌는 이유가 하나여야 한다**는 뜻.

### 위반하는 코드

```java
class Employee {
    String name;
    double salary;

    double calculatePay() {
        // 급여 계산 로직
        return salary * 1.1;
    }

    void saveToDatabase() {
        // DB 저장 로직
        System.out.println("DB에 저장: " + name);
    }

    void printReport() {
        // 보고서 출력 로직
        System.out.println(name + "의 급여: " + calculatePay());
    }
}
```

`Employee`가 "급여 계산"(비즈니스 로직), "DB 저장"(영속성), "보고서 출력"(표현/포맷팅)이라는 서로 무관한 세 가지 책임을 동시에 지고 있다. 급여 정책이 바뀌어도, DB가 바뀌어도, 리포트 양식이 바뀌어도 전부 이 클래스를 건드려야 한다. 서로 무관한 팀의 요구사항이 하나의 클래스에서 충돌한다.

### SRP를 지킨 코드

```java
class Employee {
    String name;
    double salary;
}

class PayCalculator {
    double calculate(Employee e) {
        return e.salary * 1.1;
    }
}

class EmployeeRepository {
    void save(Employee e) {
        System.out.println("DB에 저장: " + e.name);
    }
}

class PayrollReportPrinter {
    void print(Employee e, double pay) {
        System.out.println(e.name + "의 급여: " + pay);
    }
}
```

이제 각 클래스는 바뀌는 이유가 딱 하나씩이다. 급여 계산 정책이 바뀌면 `PayCalculator`만 수정하면 된다.

> **주의**: 한 클래스가 메서드를 여러 개 가져도 SRP 위반이 아니다. `PayCalculator`에 `calculate()`, `calculateWithBonus()`가 다 있어도, 전부 "급여 계산"이라는 같은 이유로 바뀐다면 SRP는 지켜진 것. 기준은 메서드 개수가 아니라 **"바뀌는 이유의 개수"**.

## 2. OCP (개방-폐쇄 원칙, Open-Closed Principle)

**확장에는 열려있고, 변경에는 닫혀있어야 한다.** 기존 코드를 건드리지 않고 새로운 기능을 추가할 수 있어야 한다.

### 위반하는 코드 (다형성 없이)

```java
void makeItSound(Object animal) {
    if (animal instanceof Dog) {
        ((Dog) animal).bark();
    } else if (animal instanceof Cat) {
        ((Cat) animal).meow();
    }
    // 새 동물이 추가될 때마다 여기 계속 추가해야 함
}
```

### OCP를 지킨 코드

```java
abstract class Animal {
    abstract void makeSound();
}

class Dog extends Animal {
    void makeSound() { System.out.println("멍멍"); }
}

class Cat extends Animal {
    void makeSound() { System.out.println("야옹"); }
}

void makeItSound(Animal animal) {
    animal.makeSound(); // 새 동물이 추가돼도 이 함수는 안 바뀜
}
```

### SRP와의 연결

SRP로 책임을 잘게 쪼개두면, 그 각각이 OCP를 지키기 쉬워진다.

```java
interface PayCalculator {
    double calculate(Employee e);
}

class RegularPayCalculator implements PayCalculator {
    public double calculate(Employee e) { return e.salary * 1.1; }
}

class ExecutivePayCalculator implements PayCalculator {
    public double calculate(Employee e) { return e.salary * 1.5 + 10000; }
}
```

`RegularPayCalculator`를 전혀 건드리지 않고 `ExecutivePayCalculator`를 추가할 수 있다 — SRP로 책임이 이미 분리돼 있었기 때문에 OCP 적용이 자연스러웠다.

## 3. LSP (리스코프 치환 원칙, Liskov Substitution Principle)

**자식 클래스는 부모 클래스를 완전히 대체할 수 있어야 한다.** 부모 타입을 쓰는 코드에 자식 객체를 넣어도 프로그램이 이상하게 동작하면 안 된다.

### 위반하는 코드 ("정사각형은 직사각형이다" 문제)

```java
class Rectangle {
    protected int width, height;
    void setWidth(int w) { width = w; }
    void setHeight(int h) { height = h; }
    int getArea() { return width * height; }
}

class Square extends Rectangle {
    @Override
    void setWidth(int w) {
        width = w;
        height = w; // 정사각형이니까 폭을 바꾸면 높이도 같이 바뀜
    }
    @Override
    void setHeight(int h) {
        width = h;
        height = h;
    }
}
```

```java
void resize(Rectangle r) {
    r.setWidth(5);
    r.setHeight(10);
    assert r.getArea() == 50; // Rectangle이면 당연히 성립
}

resize(new Rectangle()); // 통과 (5 * 10 = 50)
resize(new Square());    // 실패! (100이 됨)
```

`Rectangle`을 기대하고 짠 코드에 `Square`를 넣었더니 결과가 완전히 달라진다 — `Square`가 `Rectangle`을 대체하지 못한다.

### 사전조건 / 사후조건

- **사전조건**: 메서드를 호출하기 *전에* 호출자가 지켜야 하는 조건
- **사후조건**: 메서드 실행 *후*, 호출자가 믿고 기대해도 되는 결과

`Rectangle.setWidth(w)`는 암묵적으로 이런 사후조건을 약속한다: "`width`만 `w`로 바뀌고, `height`는 건드리지 않는다." `resize()`는 이 약속을 믿고 짜여 있다. `Square.setWidth(w)`는 `height`까지 몰래 바꿔버려서 이 사후조건을 깬다 — 이게 LSP 위반의 본질이다.

### LSP를 지킨 코드

```java
interface Shape {
    int getArea();
}

class Rectangle implements Shape {
    int width, height;
    Rectangle(int w, int h) { width = w; height = h; }
    public int getArea() { return width * height; }
}

class Square implements Shape {
    int side;
    Square(int s) { side = s; }
    public int getArea() { return side * side; }
}
```

`Rectangle`과 `Square`를 상속 관계로 억지로 묶지 않고 공통 인터페이스 `Shape`만 구현하게 하면, `Square`가 `Rectangle`의 약속을 물려받지 않으므로 문제가 사라진다.

> **핵심**: LSP는 "논리적으로 IS-A 관계가 맞냐"가 아니라 **"부모가 호출자에게 한 약속(사전조건/사후조건)을 자식이 그대로 지키느냐"**를 묻는다.

## 4. ISP (인터페이스 분리 원칙, Interface Segregation Principle)

**하나의 인터페이스가 너무 많은 기능을 담지 않고, 클라이언트에 맞게 잘게 나뉘어야 한다.**

### 위반하는 코드

```java
interface Machine {
    void print(String doc);
    void scan(String doc);
    void fax(String doc);
}

class MultiFunctionPrinter implements Machine {
    public void print(String doc) { System.out.println("인쇄: " + doc); }
    public void scan(String doc) { System.out.println("스캔: " + doc); }
    public void fax(String doc) { System.out.println("팩스: " + doc); }
}

class OldPrinter implements Machine {
    public void print(String doc) { System.out.println("인쇄: " + doc); }
    public void scan(String doc) {
        throw new UnsupportedOperationException("이 프린터는 스캔 기능이 없음");
    }
    public void fax(String doc) {
        throw new UnsupportedOperationException("이 프린터는 팩스 기능이 없음");
    }
}
```

`OldPrinter`는 인쇄만 가능한데, `Machine` 인터페이스를 구현하려니 `scan()`, `fax()`까지 억지로 구현해야 한다. 실제로는 예외만 던지는 폭탄이 숨어있는 셈이고, `Machine`에 새 기능이 추가되면 무관한 `OldPrinter`까지 고쳐야 한다.

### ISP를 지킨 코드

```java
interface Printer {
    void print(String doc);
}
interface Scanner {
    void scan(String doc);
}
interface Fax {
    void fax(String doc);
}

class MultiFunctionPrinter implements Printer, Scanner, Fax {
    public void print(String doc) { System.out.println("인쇄: " + doc); }
    public void scan(String doc) { System.out.println("스캔: " + doc); }
    public void fax(String doc) { System.out.println("팩스: " + doc); }
}

class OldPrinter implements Printer {
    public void print(String doc) { System.out.println("인쇄: " + doc); }
    // scan, fax를 억지로 구현할 필요가 없음
}
```

### SRP vs ISP — 관점의 차이

| | SRP | ISP |
|---|---|---|
| 대상 | 클래스(구현체) | 인터페이스(계약) |
| 관점 | "이 클래스는 왜 바뀌는가" — 구현하는 쪽 입장 | "이 인터페이스를 쓰는 사람이 뭘 필요로 하는가" — 사용하는 쪽 입장 |
| 위반 시 증상 | 서로 무관한 이유들로 한 클래스가 계속 수정됨 | 클라이언트가 쓰지도 않을 메서드까지 억지로 구현/인지해야 함 |

**SRP는 위반했지만 ISP는 지켜진 경우**도 있을 수 있다:

```java
interface Printable {
    void print(String doc);
}

class ReportGenerator implements Printable {
    public void print(String doc) { System.out.println("인쇄: " + doc); }

    // 인터페이스엔 없지만 클래스 내부에 여러 책임이 숨어있음
    void formatReport() { /* 포맷팅 로직 */ }
    void sendEmailReport() { /* 이메일 발송 로직 */ }
    void saveToDatabase() { /* DB 저장 로직 */ }
}
```

`Printable` 인터페이스 자체는 `print()` 하나뿐이라 ISP는 완벽하지만, `ReportGenerator` 내부는 포맷팅/이메일/DB저장까지 떠안고 있어 SRP는 위반이다. **ISP는 겉으로 드러난 계약이 깔끔한지를, SRP는 그 뒤의 구현이 하나의 책임만 갖는지를 본다** — 서로 다른 층위를 검사하는 것.

> 둘 다 핵심은 "메서드 개수를 줄여라"가 아니라 **응집도 있게 나누는 것**이다. SRP는 "구현체가 짊어진 이유의 개수를 하나로", ISP는 "계약이 각 클라이언트에게 꼭 필요한 만큼만 노출되도록" 하는 원칙이다.

**클래스 vs 인터페이스**: 클래스는 "무엇을 가지고 어떻게 동작하는지"까지 정의하는 실제 구현체(`new`로 인스턴스 생성 가능). 인터페이스는 "무엇을 할 수 있어야 하는지"만 정의하는 계약(구현 없음, 어떤 클래스가 `implements`로 약속해야 동작).

## 5. DIP (의존 역전 원칙, Dependency Inversion Principle)

**상위 모듈이 하위 모듈(구체적인 구현체)에 직접 의존하지 않고, 추상화된 인터페이스에 의존해야 한다.**

### 위반하는 코드

```java
class EmailSender {
    void sendEmail(String message) {
        System.out.println("이메일 전송: " + message);
    }
}

class NotificationService {
    private EmailSender emailSender = new EmailSender(); // 구체 클래스를 직접 생성

    void notify(String message) {
        emailSender.sendEmail(message);
    }
}
```

`NotificationService`(상위 모듈)가 `EmailSender`(하위 모듈)를 직접 `new`로 생성해 붙잡고 있다. 문자(SMS)로도 보내고 싶으면 `NotificationService`를 뜯어고쳐야 하고, 테스트 시 가짜(mock)로 바꿔치기할 방법도 없다.

### DIP를 지킨 코드

```java
interface MessageSender { // 추상화
    void send(String message);
}

class EmailSender implements MessageSender {
    public void send(String message) { System.out.println("이메일 전송: " + message); }
}

class SmsSender implements MessageSender {
    public void send(String message) { System.out.println("문자 전송: " + message); }
}

class NotificationService {
    private MessageSender sender; // 구체 클래스가 아닌 인터페이스에 의존

    NotificationService(MessageSender sender) { // 외부에서 주입받음
        this.sender = sender;
    }

    void notify(String message) {
        sender.send(message);
    }
}
```

```java
NotificationService service1 = new NotificationService(new EmailSender());
NotificationService service2 = new NotificationService(new SmsSender());
```

`NotificationService`는 `MessageSender`라는 추상화만 알 뿐, 실제 구현이 이메일인지 문자인지 모른다. 이렇게 외부에서 필요한 구현체를 넣어주는 방식을 **의존성 주입(Dependency Injection)**이라 부르며, DIP를 실현하는 대표적인 방법이다.

**"역전"이라는 이름의 이유**: 원래 자연스러운 흐름은 "상위가 하위를 알고 사용한다"이다. DIP는 이를 뒤집어 **하위 모듈(`EmailSender`)이 상위가 정의한 인터페이스(`MessageSender`)에 맞춰 자신을 구현**하게 만든다. 의존의 화살표 방향이 뒤집히는 것.

### DIP와 OCP의 연결

DIP 덕분에 `SmsSender`라는 새 구현체를 추가해도 `NotificationService`는 전혀 바뀌지 않는다 — 이것이 곧 OCP다. **DIP는 OCP를 실제로 가능하게 만드는 구체적인 방법**이다: 추상화에 의존하게 만들면, 새 구현체 추가 시 기존 코드를 건드리지 않을 수 있다.

---

## 한 줄 요약

| 원칙 | 핵심 |
|---|---|
| SRP | 클래스가 바뀌는 이유는 하나로 |
| OCP | 기존 코드를 안 건드리고 확장 가능하게 |
| LSP | 자식이 부모의 약속(사후조건)을 깨지 않게 |
| ISP | 인터페이스를 클라이언트 필요에 맞게 잘게 |
| DIP | 구체 구현이 아니라 추상화에 의존하게 |

서로 독립적이지 않다: SRP가 지켜지면 OCP가 쉬워지고, ISP가 지켜지면 SRP도 자연스러워지며, DIP는 OCP를 가능하게 하는 구체적 수단이다.

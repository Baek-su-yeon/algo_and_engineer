# HTTP/HTTPS 관련 QnA

## 1. HTTP/2.0
- 등장 배경: 기존 HTTP/1.1은 한 번에 하나의 요청과 응답만 처리할 수 있는 구조(HOL Blocking)여서, 웹페이지에 포함된 이미지나 스크립트 등 리소스가 많아지면 로딩 속도가 느려지는 한계가 있음.
- 특징
  - Multiplexing: 하나의 TCP 연결을 통해 여러 개의 요청과 응답을 동시에 주고받을 수 있어 병목 현상을 해결
  - HPACK(헤더압축): 반복 전송되는 중복 HTTP 헤더를 압축해 네트워크 대역폭 사용량 감소.
  - Server Push: 클라이언트가 요청하지 않아도 서버가 미리 필요한 리소스를 클라이언트에게 보내줄 수 있음.
- HTTPS와의 관계: HTTP/2.0 표준 스펙상 암호화가 필수는 아니나, 크롬과 파이어폭스 등 주요 브라우저들이 반드시 TLS 암호화(HTTPS)가 적용된 환경에서만 HTTP/2.0을 지원하도록 정책을 정했기 때문에 사실상 HTTPS와 함께 사용함.

## 2. REST API와 HTTP에 대해 설명하라.
- HTTP와의 관계: REST API는 HTTP 프로토콜을 기반으로 웹의 장점을 최대한 활용하기 위해 만들어진 아키텍처 스타일, 즉 규칙모음임. REST API = HTTP위에서 동작함.
- 핵심 요소
  - Resource: 모든 자원은 고유한 URI로 식별
  - 행위(Verb, HTTP 메서드): 자원에 대한 처리는 HTTP 메서드를 통해 표현. `GET`, `POST`, `PUT`, `PATCH`, `DELETE` 등
  - Representation: 클라이언트와 서버가 주고 받는 데이터 형식은 주로 JSON이나 XML을 사용.
- 특징: HTTP의 'Stateless'와 캐시 기능 등을 그대로 활용해 서버와 클라이언트 간의 결합도를 낮추고 독립적으로 확장할 수 있게 해줌.

## 3. 관련해서 발생하는 보안 위험 및 해킹 종류
- 스니핑(Sniffing, 도청): HTTP는 암호화되지 않은 평문을 전송하니까 네트워크 경로 중간에서 패킷 가로채면 사용자 아이디, 비밀번호 등 민감한 정보를 그대로 탈취 가능.
- 스푸핑(Spoofing, 위장): 공격자가 네트워크 상에서 정상 서버인 척 위장해서 사용자 정보를 가로채거나 가짜 웹사이트로 유도함. HTTPS는 CA 인증서를 통해 서버 신원을 검증하니까 이걸 막을 수 있음.
- 중간자 공격(Man-in-the-Middle Attack, MitM): 클라이언트와 서버 사이에 공격자가 끼어들어 통신 내용을 가로채거나 조작하는 공격. 암호화와 무결성이 보장되지 않는 환경에서 주로 발생.
- 세션 하이재킹(Session Hijacking): 로그인 후 발급되는 세션 ID나 토큰을 탈취해 사용자 권한을 도용함. 전송 구간이 암호화되지 않으면 쉽게 노출됨.

## 4. TLS
- 정의: Transport Layer Security. 네트워크 계층에서 통신을 암호화해 기밀성/무결성을 제공하는 보안 프로토콜. 과거에 사용되던 SSL의 개선된 표준 버전임. 보통 SSL/TLS로 함께 묶어서 부름.
- 작동 원리 = hand-shake
  - 클라이언트와 서버가 연결 맺을 때 TLS Handshake 과정을 거침.
  - 이 과정에서 서로 사용할 암호화 알고리즘을 정하고, 서버의 인증서를 검증한 뒤, 데이터를 실제로 암호화/복호화할 대칭키를 안전하게 교환.
- 역할: 전송되는 모든 데이터의 암호화(기밀성), 데이터 변조 방지(무결성), 그리고 통신 상대방의 신원 확인(인증)을 수행하여 안전한 웹 생테계 지탱하는 핵심 기술.


## 5. HTTP와 달리 HTTPS 관리에서 성능 부담은 어떻게 일어나는가?
- 초기 연결 지연(Handshake Overheaad)
  - HTTP는 TCP연결 직후 바로 데이터를 주고 받을 수 있지만, HTTPS는 TCP 연결 후 TLS Handshake 과정(인증서 검증 및 대칭키 교환)을 추가로 거쳐야하므로 최초 접속 시 지연 시간, 즉 Latency가 발생.
- 암호화/복호화 연산 비용
  - 데이터 주고받을 때마다 CPU가 암호화/복호화 연산을 수행해야 하므로 서버와 클라이언트 모두에 미세한 연산 부담 가중.
- 현대의 성능 개선
  - 과거에는 이런 오버헤드가 부담이었지만, 하드웨어 성능 발전과 TLS1.3 같은 최신 프로토콜 도입으로 Handshake 왕복 횟수가 줄어들고 Seesion Resumption(세션 재개) 기능이 최적화되면서 현재는 체감하기 어려울 정도로 성능 차이가 없음.

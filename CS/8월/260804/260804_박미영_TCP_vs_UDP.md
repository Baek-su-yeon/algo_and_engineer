### 1. TCP와 UDP는 어디에서 사용될까?

- OSI 7계층 중 전송 계층 프로토콜
    - **OSI 7계층**
        - 카카오톡으로 친구에게 **“안녕”**을 보낸다고 가정하면 아래와 같은 과정을 거침.
        - **7계층 - 응용 계층**
            - 사용자가 직접 이용하는 서비스와 가장 가까운 계층
            - 카카오톡에서 “안녕”을 입력하고 전송 버튼을 누름
            - 카카오톡이 메시지를 서버로 보낼 준비를 함
            - **사용자가 네트워크 서비스를 이용하는 단계**
        - **6계층 - 표현 계층**
            - 데이터를 통신에 적합한 형태로 변환하는 계층
            - “안녕”이라는 글자를 컴퓨터가 처리할 수 있는 데이터로 변환
            - 필요하면 데이터를 암호화하거나 압축함
            - **메시지의 형식을 바꾸고 암호화하는 단계**
        - **5계층 - 세션 계층**
            - 나와 카카오톡 서버 사이의 통신 연결 상태를 관리
            - 내가 카카오톡에 로그인되어 있는지 확인
            - 서버와의 연결이 유지되고 있는지 관리
            - 통신이 끊기면 다시 연결함
            - **대화가 계속 이어질 수 있도록 연결 상태를 관리하는 단계**
        - **4계층 - 전송 계층**
            - 메시지를 상대방 프로그램까지 어떤 방식으로 전달할지 담당
            - 데이터를 작은 단위로 나눔
            - 포트 번호를 이용해 카카오톡 서버 프로그램을 구분
            - TCP를 사용한다면 데이터가 제대로 도착했는지 확인하고, 손실되면 다시 보냄
            - **컴퓨터에서 실행 중인 목적지 프로그램을 구분하고, 데이터를 어떤 방식으로 전달할지 관리하는 단계**
        - **3계층 - 네트워크 계층**
            - IP 주소를 이용해 목적지 컴퓨터를 찾아감.
            - 카카오톡 서버의 IP 주소를 확인
            - 여러 네트워크와 라우터를 거쳐 서버까지 이동할 경로를 정함
            - **카카오톡 서버가 있는 컴퓨터까지 찾아가는 단계**
        - **2계층 - 데이터 링크 계층**
            - 현재 연결된 가까운 네트워크 장치까지 데이터를 전달함.
            - 내 스마트폰에서 공유기까지 데이터를 전달
            - MAC 주소를 이용해 같은 네트워크에 있는 장치를 구분
            - 전송 중 오류가 있는지 확인함
            - **같은 네트워크 안에서 다음 장치로 데이터를 전달하는 단계**
        - **1계층 - 물리 계층**
            - 데이터를 실제 전기 신호나 전파로 전송함.
            - 스마트폰이 데이터를 와이파이 전파나 이동통신 신호로 보냄
            - 케이블, 광신호, 전파 등을 통해 실제로 이동함
            - **데이터를 실제 신호로 바꾸어 전송하는 단계**
    - **TCP와 UDP는 전송 계층에서 뭘 하는가?**
        - 전송 계층은 데이터를 컴퓨터 안의 어떤 프로그램에, 어떤 방식으로 전달할지 관리하는 계층
        - 카카오톡 메시지를 보낸다고 하면 전송 계층에서는
            1. 카카오톡이 만든 데이터를 전송하기 적당한 크기로 나눔
            2. 포트 번호를 붙여 카카오톡 서버의 프로그램으로 가도록 함
            3. 데이터를 어떤 방식으로 보낼지 결정함
            4. 상대방에서는 나뉜 데이터를 받아 원래 형태로 복원한 뒤 카카오톡 프로그램에 전달함 
        - 이때 전송 방식이 두 가지
            - **TCP : 도착 여부와 순서를 확인하고, 손실되면 다시 보냄**
            - **UDP : 도착 여부를 확인하지 않고 바로 보냄**
    - **TCP와 UDP가 데이터를 보내는 방식이 왜 다른가**
        - **TCP**
            - 데이터를 보내기 전에 상대방과 연결을 확인함
            - **⇒ 연결형**
            - 통신 가능해? → 가능해 → 확인했어 → 데이터 전송
            - **상대방에게 전화해서 주소와 수령 가능 여부를 확인한 뒤, 등기로 보내고 수령 확인까지 함**
        - **UDP**
            - 상대방에게 준비됐는지 확인하지 않고 목적지의 IP 주소와 포트 번호를 보고 바로 데이터를 보냄
            - **⇒ 비연결형**
            - 데이터 전송
            - **주소만 적어서 일반 우편함에 바로 넣음**
- 애플리케이션 프로세스 간 데이터 전달 담당

### 2. TCP란?

- 데이터의 도착과 순서를 보장하고, 손실된 데이터는 재전송하는 연결형 프로토콜
- **연결 설정 : 3-way handshake**
    
    ```python
    클라이언트 → 서버 : SYN
    클라이언트 ← 서버 : SYN + ACK
    클라이언트 → 서버 : ACK
    ```
    
- 위 과정을 통해 양쪽이 모두 데이터를 주고받을 준비가 되었는지 확인
    - **⇒ 전화해서 상대방이 통신 가능한지 서로 확인하는 과정**
- **3-way handshake 자세한 과정**
    - **SYN과 ACK**
        - **SYN(Synchronize)** : “연결을 시작하고 싶어. 통신 준비됐어?”
        - **ACK(Acknowledgment)** : “네가 보낸 메시지를 잘 받았어.”
        - SYN이나 ACK라는 별도의 물건을 보내는 게 아니라, TCP 헤더 안에 있는 제어 비트(플래그)
    - **3-way handshake 과정**
        1. **클라이언트 → 서버 : `SYN`**
            
            ```python
            클라이언트 : 서버야, 나랑 통신할 수 있어?
            ```
            
            - 서버가 `SYN`을 받으면 클라이언트에서 서버로 데이터가 전달될 수 있다는 것을 알게 됨.
        2. **서버 → 클라이언트 : `SYN + ACK`**
            
            ```python
            서버 : 네 요청 잘 받았어(ACK). 나도 통신할 준비가 됐어(SYN).
            ```
            
            - 클라이언트가 이 응답을 받으면 다음을 알게 됨.
                - 내가 보낸 요청이 서버에 도착했음
                - 서버가 보낸 응답도 나에게 도착했음
                - 서버가 통신할 준비가 됐음.
        3. **클라이언트 → 서버 : `ACK`**
            
            ```python
            클라이언트 : 네 응답도 잘 받았어.
            ```
            
            - 서버가 마지막 `ACK`를 받으면, 서버도 자신의 응답이 클라이언트에게 정상적으로 도착했다는 것을 알게 됨.

### 3. TCP는 어떻게 신뢰성을 보장할까?

- TCP의 핵심은 단순히 “연결한다”가 아니라 다음 기능을 통해 신뢰성을 보장
    - **순서 번호** : 데이터의 순서를 확인
    - **ACK** : 데이터를 정상적으로 받았음을 알림
    - **재전송** : 데이터가 손실되면 다시 전송
    - **체크섬** : 전송 중 데이터 오류 확인
    - **흐름 제어** : 수신자가 처리할 수 있는 속도에 맞춰 전송
    - **혼잡 제어** : 네트워크가 혼잡되면 전송량을 줄임
- **좀 더 자세한 버전**
    - 그렇다면 TCP가 왜 신뢰성 있는 프로토콜인가?
    1. **데이터가 제대로 도착했는지 확인**
        - TCP는 데이터를 보낸 뒤 수신자로부터 ACK를 받음.
        
        ```python
        송신자: 데이터 보냄
        수신자: 데이터 잘 받았어 → ACK
        ```
        
        - 일정 시간 동안 ACK가 오지 않으면 데이터가 손실됐다고 판단하고 다시 보냄.
    2. **순서 번호로 데이터 순서 보장**
        - TCP는 전송하는 데이터에 순서 번호를 붙임.
        
        ```python
        1번 데이터
        2번 데이터
        3번 데이터
        ```
        
        - 데이터가 `1 -> 3 -> 2` 순서로 도착하더라도 수신 측에서 `1 -> 2 -> 3`으로 다시 정렬할 수 있음.
    3. **손실된 데이터 재전송**
        - 2번 데이터가 오지 않았다면 수신자는 정상적으로 받은 지점까지만 ACK를 보내고, 송신자는 누락된 데이터를 다시 전송함.
        
        ```python
        1번 도착
        2번 손실
        3번 도착
        → 2번 다시 전송
        ```
        
    4. **흐름 제어**
        - 송신자가 데이터를 너무 빠르게 보내 수신자가 처리하지 못하는 상황을 방지함.
        - 수신자의 처리 속도에 맞춰 송신 속도를 조절하는 기능
    5. **혼잡 제어**
        - 네트워크 자체가 혼잡할 때 전송량을 줄임.
    6. **연결 종료**
        - 통신이 끝나면 일반적으로 4-way handshake를 통해 연결을 종료함.
        - 깊게 알 필요는 없으나, TCP는 연결을 설정하고 종료하는 절차가 있다는 정도만 알면 됨.

### 4. UDP란?

- 연결 설정 없이 데이터를 바로 보내는 비연결형 프로토콜

```python
송신자 → 데이터 전송 → 수신자
```

- **UDP는 연결을 설정하지 않고도 어떻게 전송하는가?**
    1. **애플리케이션이 UDP에 데이터를 전달**
    2. **UDP 헤더를 붙임**
        - 데이터 앞에 출발지 포트 번호, 목적지 포트 번호 등의 정보를 붙임
    3. **IP 계층으로 전달**
        - UDP는 목적지 IP 주소를 이용한 실제 전송을 네트워크 계층의 IP에 맡김.
    4. **목적지 컴퓨터에 도착**
        - 목적지 컴퓨터에서는 UDP 헤더의 포트 번호를 확인함.
        - 해당 포트를 사용하는 프로그램에 데이터를 전달함.
- TCP와 달리 다음 기능을 제공 X
    1. **연결 설정을 하지 않음.**
        - TCP처럼 3-way handshake를 하지 않음
        - 상대방이 통신 가능한 상태인지 확인하지 않고 데이터를 보냄
        - 연결을 설정하는 데 필요한 시간이 들지 않아 지연이 작음.
    2. **데이터 도착을 확인하지 않음**
        - 데이터를 보낸 뒤 수신자로부터 ACK를 기다리지 않음
        - 송신자는 데이터가 정상적으로 도착했는지 기본적으로 알 수 없음
        
        ```python
        송신자 : 데이터 보냄
        수신자 : 응답하지 않음
        ```
        
        - 여기서 수신자가 실제로 데이터를 받지 못했다는 뜻은 아님. UDP 프로토콜 자체가 받았는지 확인하지 않는다는 뜻
    3. **손실된 데이터를 재전송하지 않음**
        - 데이터가 중간에 사라져도 UDP가 다시 보내지 않음
        - TCP처럼 ACK가 오지 않았다고 판단해 재전송하는 기능이 없음
        - 따라서 데이터 일부가 손실도리 수 있지만, 손실되 데이터를 기다리지 않고 다음 데이터를 계속 받을 수 있음.
    4. **순서를 보장하지 않음**
        - UDP는 데이터가 보낸 순서대로 도착한다고 보장하지 않음
        - TCP는 순서 번호를 이용해 데이터를 다시 정렬하지만, UDP는 기본적으로 순서를 다시 맞춰주지 않음.
        - 순서가 필요하다면 애플리케이션에서 직접 순서 번호를 붙이고 정렬해야 함.
    5. **오류를 확인할 수는 있지만 복구하지 않음**
        - UDP에도 체크섬이 있어 데이터가 전송 중 손상되었는지 확인할 수 있음.
        - 오류가 발견된 데이터는 버릴 수 있지만, UDP가 직접 재전송하여 복구하지는 않음.
    6. **흐름 제어를 하지 않음**
        - UDP는 수신자가 데이터를 처리할 수 있는 속도를 확인하지 않음
        
        ```python
        송신자 : 계속 데이터 전송
        수신자 : 처리 속도가 느려도 UDP가 전송 속도를 조절하지 않음
        ```
        
        - 따라서 송신자가 너무 빠르게 보내면 수신자가 일부 데이터를 처리하지 못하거나 버릴 수 있음.
    7. **혼잡 제어를 하지 않음**
        - UDP 자체에는 네트워크의 혼잡 상태를 확인하고 전송량을 줄이는 기능이 없음.
- **UDP가 빠른 이유**
    - 위와 같은 기능을 제공하지 않기 때문에 빠르게 지연이 작음.
    - 무조건 전송 속도가 빠르다는 게 아니라 신뢰성을 보장하기 위한 추가 확인 절차가 적기 때문에 전송 지연과 처리 부담이 상대적으로 작음.

### 5. TCP와 UDP 비교

| 구분 | TCP | UDP |
| --- | --- | --- |
| 연결 방식 | 연결형 | 비연결형 |
| 신뢰성 | 높음 | 기본적으로 보장하지 않음 |
| 데이터 순서 | 보장 | 보장하지 않음 |
| 손실 시 처리 | 재전송 | 재전송하지 않음 |
| 전송 단위 | 스트림 | 데이터그램 |
| 헤더 크기 | 최소 20바이트 | 8바이트 |
| 흐름·혼잡 제어 | 있음 | 없음 |
| 속도·지연 | 상대적으로 느리고 지연이 큼 | 상대적으로 빠르고 지연이 작음 |
| 주요 목적 | 정확한 전달 | 빠른 전달 |
- **전송 단위 보충 설명**
    - TCP 스트림 : 데이터를 경계 없는 연속된 바이트 흐름으로 처리
    - UDP 데이터그램 : 보낸 메시지 단위를 그대로 구분하여 처리
    - 예를 들어 UDP에서 `안녕`, `반가워`를 두 번 보내면 두 개의 데이터그램으로 구분됨.
    - TCP는 연속된 데이터 흐름으로 보기 때문에 애플리케이션이 메시지 경계를 직접 구분해야 함.

### 6. 실제 서비스에서는 어떻게 사용될까?

- **TCP가 적합한 경우**
    - 데이터가 조금이라도 누락되면 안 되는 서비스에 사용됨.
    - 웹 통신
    - 파일 전송: FTP
    - 이메일: SMTP
    - 원격 접속: SSH
    - 금융 거래 및 로그인 정보 전달
    - 예를 들어 파일을 내려받을 때 일부 데이터가 누락되면 파일이 손상되므로 TCP가 적합함.
- **UDP가 적합한 경우**
    - 일부 데이터가 손실되더라도 빠르게 전달하는 것이 더 중요한 서비스에 사용됨.
    - 음성 통화와 화상 회의
    - 실시간 게임
    - 실시간 영상 전송
    - DNS 질의
    - DHCP
    - NTP
    - 영상 통화에서는 오래된 패킷을 재전송받는 것보다 다음 화면을 빠르게 받는 것이 더 중요함.

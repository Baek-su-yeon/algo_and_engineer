# 오버라이딩(Overriding) vs 오버로딩(Overloading)

> 직무면접 대비 CS 용어 정리 노트

---

## 1. 다형성(Polymorphism)이란?

**같은 이름의 호출이, 실제 객체(또는 입력)가 무엇이냐에 따라 다르게 동작하는 것**을 말한다.

다형성이라는 큰 목표를 구현하는 두 가지 방법이 오버라이딩(런타임 다형성)과 오버로딩(컴파일타임 다형성)이다.

### 다형성이 없을 때

새로운 동물이 추가될 때마다 분기문을 계속 고쳐야 한다.

```java
void makeItSound(Object animal) {
    if (animal instanceof Dog) {
        ((Dog) animal).bark();
    } else if (animal instanceof Cat) {
        ((Cat) animal).meow();
    } else if (animal instanceof Bird) {
        ((Bird) animal).tweet();
    }
    // 새 동물이 추가될 때마다 여기 계속 추가해야 함
}
```

### 다형성이 있을 때

새로운 동물 클래스를 추가해도 이 함수는 한 줄도 고칠 필요가 없다.

```java
abstract class Animal {
    abstract void makeSound();
}

class Dog extends Animal {
    void makeSound() { System.out.println("멍멍"); }
}

class Cat extends Animal {
    void makeSound() { System.out.println("야옹"); }
}

void makeItSound(Animal animal) {
    animal.makeSound(); // Dog든 Cat이든 Fish든 신경 쓰지 않음
}
```

이렇게 "기존 코드를 건드리지 않고도 새로운 종류를 추가할 수 있는 확장성"을 **개방-폐쇄 원칙(OCP, Open-Closed Principle)** 이라고 부른다.

---

## 2. 오버라이딩(Overriding)

상속 관계에서 **부모 클래스의 메서드를 자식 클래스가 재정의**하는 것. 메서드명, 매개변수, 반환형은 모두 동일하지만 내부 구현만 다르다. 자식 클래스가 부모의 동작을 자신만의 방식으로 바꿔 쓰고 싶을 때 사용한다.

```java
class Animal {
    void makeSound() { System.out.println("동물이 소리를 냅니다"); }
}

class Dog extends Animal {
    @Override
    void makeSound() { System.out.println("멍멍"); } // 재정의
}
```

- 상속이 전제되어야 함
- 런타임 다형성 / 동적 바인딩
- 기존 기능을 새롭게 정의하는 것

---

## 3. 오버로딩(Overloading)

상속 관계가 없어도 되며, **같은 클래스 내에서 메서드 이름은 같지만 매개변수의 개수나 타입이 다를 때** 여러 개의 메서드를 정의하는 것. 같은 기능을 다양한 입력 형태로 유연하게 쓸 수 있게 해준다.

```java
class Calculator {
    int add(int a, int b) { return a + b; }
    double add(double a, double b) { return a + b; }
    Vector add(Vector a, Vector b) { return a.plus(b); }
}
```

- 상속 불필요
- 컴파일타임 다형성 / 정적 바인딩
- 하나의 이름으로 여러 기능을 확장하는 것

---

## 4. 왜 둘 다 필요한가?

같은 다형성이라는 목표를, 상황에 따라 다르게 풀어낸 것이다.

| 구분 | 해결하는 문제 |
|---|---|
| 오버라이딩 | 상속 계층에서 **확장 가능**하게 (OCP) |
| 오버로딩 | 같은 이름 아래 여러 입력 형태를 **편하게** 사용 |

둘 다 결국 "코드를 쓰는 사람 입장에서 신경 쓸 게 줄어드는 것"이 목표라는 공통점이 있다.

---

## 5. 왜 오버로딩은 정적 바인딩, 오버라이딩은 동적 바인딩인가

**바인딩(Binding)** = "메서드 호출 코드"와 "실제로 실행될 메서드의 본체"를 연결하는 행위.

### 오버로딩 → 정적 바인딩 (컴파일타임 다형성)

```java
add(3, 5); // 매개변수가 int 2개 → 컴파일러가 코드만 보고도 즉시 확정
```

매개변수의 개수/타입만 보면 어떤 메서드를 호출할지 컴파일러가 바로 알 수 있다. 실행해볼 필요가 없다. → **컴파일 시점에 실행 코드가 고정**되므로 정적 바인딩.

### 오버라이딩 → 동적 바인딩 (런타임 다형성)

```java
Animal a = getAnimalFromServer(); // 서버 응답을 봐야 실제 타입을 앎
a.makeSound();
```

`a`의 실제 타입이 무엇인지는 프로그램이 실제로 그 줄을 실행해봐야 알 수 있다. → **실행 시점에 실행 코드가 결정**되므로 동적 바인딩.

> **주의할 점**: "이 코드에서 실제 타입을 추론할 수 있는지"가 기준이 아니다. `Animal a = new Dog();`처럼 사람이 봤을 때 뻔히 보이는 케이스라도, 언어는 "이 메서드가 오버라이딩 가능한 인스턴스 메서드인가"만 보고 무조건 런타임 룩업 방식으로 컴파일한다. 개별 케이스의 추론 가능 여부가 아니라, **언어가 이 호출을 어떻게 해석하기로 정했는지**가 기준이다.

---

## 6. vtable(가상 함수 테이블)로 보는 동적 바인딩의 실체

- 클래스마다 자신이 가진 가상 메서드들의 **실제 코드 주소를 모아둔 테이블(vtable)**을 하나씩 갖는다.
- **같은 이름의 메서드는 부모/자식 관계에서 항상 같은 슬롯 번호**에 저장된다. `Animal::makeSound`가 슬롯 0번이면, `Dog`가 오버라이딩한 `makeSound`도 무조건 슬롯 0번 — 다만 그 슬롯에 담긴 실제 주소만 `Dog::makeSound()`로 바뀌어 있을 뿐이다.
- 객체 하나하나는 자신이 어떤 클래스의 vtable을 써야 하는지 가리키는 숨은 포인터, **vptr**을 갖고 있다.

`a.makeSound()` 호출 시 동작 순서:

1. `a`의 vptr을 따라가서 어떤 클래스의 vtable을 쓰는지 확인 (실행 시점에만 알 수 있음)
2. 그 vtable에서 슬롯 0번을 찾아감 (이름 검색이 아니라 배열 인덱스 접근 — 매우 빠름)
3. 슬롯에 저장된 실제 함수 주소로 점프해서 실행

**컴파일 시점에 고정되는 것**: "이 호출은 슬롯 0번을 참조한다"는 사실 (클래스 설계 시점에 확정)
**실행 시점에 결정되는 것**: `a`의 vptr이 실제로 어떤 vtable을 가리키는지 (Dog냐 Cat이냐)

### 오버로딩이 vtable에 안 들어가는 이유

오버로딩은 실행할 코드를 결정하는 데 필요한 정보(매개변수 개수/타입)가 전부 컴파일 시점 코드에 이미 적혀 있다. 실행 시점까지 갈 필요 자체가 없다. vtable은 "컴파일 시점엔 모르지만 실행 시점엔 알 수 있는 정보(실제 객체 타입)"를 나중에 찾기 위한 장치인데, 오버로딩에는 애초에 그런 정보가 없다.

C++에서는 한 걸음 더 나아가, 오버로딩된 함수들은 **이름 맹글링(name mangling)**을 거쳐 매개변수 타입이 함수 이름 자체에 인코딩된다.

```cpp
void add(int a, int b);       // 내부적으로: _Z3addii
void add(double a, double b); // 내부적으로: _Z3adddd
```

컴파일러는 `add(3, 5)`를 보는 순간 `_Z3addii`라는 완전히 다른 이름의 함수로 링커 단계에서 바로 연결한다. vtable 같은 간접 참조 자체가 필요 없다.

## 7. 언어별 구현 차이

동적 바인딩(런타임에 실제 타입을 보고 메서드를 찾는다)이라는 개념은 공통이지만, 그 룩업을 **어느 계층에서 수행하느냐**가 언어마다 다르다.

| 언어 | 구현 방식 |
|---|---|
| **Java** | 컴파일 결과물(바이트코드)에 `invokevirtual`이라는 명령어를 심어둔다. JVM이 실행 시점에 이 명령어를 보고 vptr → vtable → 슬롯 룩업을 대신 수행한다. |
| **C++** | 가상 머신이 없다. 컴파일러가 "vptr 읽어라 → 슬롯 인덱스 계산 → 그 주소로 점프"하는 과정을 CPU가 바로 실행할 수 있는 기계어 명령어(메모리 읽기 + 간접 호출)로 직접 풀어서 박아넣는다. |
| **Python** | 부록 참고 |

> Java와 C++ 둘 다 vtable 방식을 쓰는 건 동일하다. 차이는 그 룩업 과정을 **JVM이라는 한 단계 위 계층이 대신 해주느냐(Java)**, **컴파일러가 그 계층 없이 기계어로 직접 풀어버리느냐(C++)**의 차이다.

## 부록: 파이썬에서의 오버로딩 / 오버라이딩

파이썬은 자바나 C++과 근본적으로 다른 타입 시스템(동적 타이핑)을 갖고 있어서, 두 개념이 그대로 대응되지 않는다.

### 오버라이딩

파이썬의 오버라이딩은 자바/C++과 개념적으로는 동일하다 — 자식 클래스가 부모의 메서드를 같은 이름으로 재정의하면 된다.

```python
class Animal:
    def make_sound(self):
        print("동물이 소리를 냅니다")

class Dog(Animal):
    def make_sound(self):  # 오버라이딩
        print("멍멍")

a = Dog()
a.make_sound()  # "멍멍"
```

다만 그 **내부 동작 방식**은 vtable과 다르다. 파이썬 객체는 슬롯 기반 테이블이 아니라, 클래스와 인스턴스가 각각 `__dict__`(이름→값 매핑)를 갖고 있다. 메서드를 호출하면 파이썬은:

1. 인스턴스의 `__dict__`에서 이름을 찾는다 (보통 없음)
2. 없으면 `type(a).__mro__` (Method Resolution Order — 상속 계층을 정의된 순서로 나열한 리스트)를 따라가며 각 클래스의 `__dict__`에서 이름을 찾는다
3. 찾은 첫 번째 메서드를 실행한다

즉 자바/C++처럼 "고정된 슬롯 인덱스"로 찾는 게 아니라, **매번 문자열 이름으로 딕셔너리를 탐색**한다. vtable보다 유연하지만(슬롯을 미리 정해둘 필요가 없음) 상대적으로 느리다.

### 오버로딩

파이썬은 **전통적 의미의 오버로딩을 지원하지 않는다.** 같은 이름의 메서드를 여러 번 정의하면, 나중에 정의된 것이 앞의 것을 덮어써버린다.

```python
class Calculator:
    def add(self, a, b):
        return a + b
    def add(self, a, b, c):  # 위의 add를 완전히 덮어씀
        return a + b + c

calc = Calculator()
calc.add(1, 2)  # TypeError! 2개짜리 add는 이제 존재하지 않음
```

이는 파이썬 함수 정의가 "이름 → 함수 객체" 딕셔너리에 값을 대입하는 것과 동일하기 때문이다. 같은 키에 두 번 대입하면 뒤의 값만 남는다.

대신 파이썬은 오버로딩이 해결하려던 문제(같은 이름으로 다양한 입력을 유연하게 받고 싶다)를 다른 방식으로 푼다.

**1) 기본값(default argument) + 가변 인자**

```python
def add(a, b, c=0):
    return a + b + c

add(1, 2)     # 3
add(1, 2, 3)  # 6
```

**2) `*args`, `**kwargs`로 임의 개수의 인자 처리**

```python
def add(*args):
    return sum(args)

add(1, 2)        # 3
add(1, 2, 3, 4)  # 10
```

**3) 덕 타이핑(duck typing)**

파이썬은 타입을 명시하지 않기 때문에, 애초에 "타입이 다르면 다른 함수"라는 개념 자체가 희미하다. `+` 연산도 정수든 문자열이든 리스트든 같은 코드로 동작한다 — 타입 검사는 실행 시점에 그 객체가 해당 연산을 지원하는지로 결정된다.

```python
def combine(a, b):
    return a + b

combine(1, 2)        # 3
combine("a", "b")    # "ab"
combine([1], [2])    # [1, 2]
```

**4) 연산자 오버로딩은 `__dunder__` 메서드로 지원**

정확히 말하면 파이썬은 "메서드 오버로딩"은 없지만 **연산자 오버로딩**은 지원한다. 이는 클래스가 `__add__`, `__eq__` 같은 특수 메서드를 정의하는 방식이며, 오버라이딩과 원리가 같다(부모/object의 기본 동작을 재정의).

```python
class Vector:
    def __init__(self, x, y):
        self.x, self.y = x, y
    def __add__(self, other):  # + 연산자를 재정의
        return Vector(self.x + other.x, self.y + other.y)
```

**5) 정말 타입별 분기가 필요하면 `functools.singledispatch`**

```python
from functools import singledispatch

@singledispatch
def process(value):
    print(f"기본 처리: {value}")

@process.register
def _(value: int):
    print(f"정수 처리: {value}")

@process.register
def _(value: str):
    print(f"문자열 처리: {value}")

process(10)     # "정수 처리: 10"
process("hi")   # "문자열 처리: hi"
```

이건 데코레이터를 이용해 "타입별로 다른 함수를 등록해두고, 실행 시점에 인자 타입을 보고 골라 쓰는" 방식이라, 사실상 파이썬 방식으로 오버로딩을 흉내 낸 것이다.

### 요약

| | 자바/C++ | 파이썬 |
|---|---|---|
| 오버라이딩 원리 | vtable 슬롯 인덱스 | `__mro__`를 따라가는 이름 탐색 |
| 오버로딩 | 언어 차원에서 지원 (컴파일러가 시그니처로 구분) | 지원 안 함 → 기본값/가변인자/덕타이핑/`singledispatch`로 대체 |

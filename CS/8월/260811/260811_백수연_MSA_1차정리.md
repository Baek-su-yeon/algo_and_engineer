> 직무면접 대비 CS 용어 정리 노트

## 0. 설명 전략 — 계층(Tier)을 나눠서 답하기

MSA는 오버라이딩/오버로딩, SOLID처럼 하나의 개념으로 완결되지 않고, **여러 하위 개념(인프라 요소)이 맞물려야 성립하는 시스템**이다. 그래서 한 번에 다 설명하려 하면 answer가 산만해지거나 너무 길어진다. 실전에서는 아래처럼 **계층을 나눠, 상대가 파고드는 만큼만 깊이 들어가는 방식**이 효과적이다.

**Tier 1 — 기본형 (약 30초)**

> "MSA는 하나의 거대한 애플리케이션을 독립적으로 배포 가능한 작은 서비스 단위로 나누고, 서비스끼리는 API로 통신하게 하는 아키텍처입니다. 서비스별로 확장하고 유지보수할 수 있다는 장점이 있지만, 서비스 간 통신 비용, 분산 트랜잭션 관리, 운영 복잡도가 늘어난다는 단점이 있습니다."

**Tier 2 — "실제로 어떻게 운영돼요?"라고 물으면 (이름만 나열)**

> "실제로 운영하려면 요청을 받는 진입점, 트래픽을 나눠주는 로드 밸런서, 서비스 위치를 찾아주는 서비스 디스커버리, 그리고 배포를 자동화하는 CI/CD와 컨테이너 오케스트레이션 같은 인프라가 함께 필요합니다."

**Tier 3 — 꼬리 질문 하나당 하나씩만 (미리 준비만, 먼저 꺼내지 않기)**

각 인프라 요소의 상세 정의는 아래 3장에서 정리.

## 1. MSA란 무엇인가

하나의 거대한 모놀리식 애플리케이션을 **작은 단위의 독립적인 서비스들**로 분리하여 개발·배포·운영하는 아키텍처. 각 서비스는 독립적으로 배포 가능하며, API를 통해 통신한다.

### 장점
- **독립 배포**: 한 서비스만 고쳤으면 그 서비스만 재배포하면 됨
- **부분 확장 = 자원 효율성**: 트래픽이 몰리는 서비스만 골라서 확장 가능 (모놀리식은 전체를 다 늘려야 함)
- **유지보수 용이**: 서비스 경계가 명확하면 한 팀이 한 서비스만 책임지고 독립적으로 일할 수 있음

### 단점
- **서비스 간 통신 복잡도/네트워크 비용**: 함수 호출 한 번이면 됐던 것이 네트워크 호출이 됨 — 느려지고 실패 가능성 생김
- **분산 트랜잭션/데이터 일관성 문제**: 서비스마다 DB가 따로라서, 여러 서비스에 걸친 작업을 하나의 트랜잭션으로 묶을 수 없음 (→ 5장 참고, Saga 패턴 등으로 보완)
- **운영 관리 복잡도**: 서비스가 많아지면 모니터링, 로그 추적, 장애 원인 파악이 어려워짐

### 설계 핵심
**서비스 경계를 명확히 정의하는 것**이 핵심. 이는 SOLID의 **SRP(단일 책임 원칙)를 시스템 전체 레벨로 확장**한 것과 같다 — 하나의 서비스가 여러 비즈니스 책임(예: 결제+배송+재고)을 동시에 떠안으면 안 되고, 독립적으로 변경/배포될 이유가 하나여야 한다.

### "요즘 프로그램은 다 MSA 아닌가?" — 아니다

MSA는 "더 나은 기술이라 다들 쓰는 것"이 아니라 **규모·조직 상황에 따른 트레이드오프**다.

- **MSA 대표 예시 — Netflix**: 2008년 데이터베이스 손상으로 3일간 서비스가 마비된 대형 장애를 계기로, AWS 기반 마이크로서비스로 약 7년(2009~2016)에 걸쳐 점진적으로 전환. 현재 700개 이상의 마이크로서비스로 운영 중. Eureka(서비스 디스커버리), Zuul(API 게이트웨이) 등의 유명 오픈소스 도구가 이 과정에서 Netflix가 직접 만든 것.
- **모놀리식(모듈러 모놀리스) 대표 예시 — Shopify**: 60만 개 이상의 가맹점, 연간 2000억 파운드 이상의 거래액을 처리하는 세계 최대급 이커머스 플랫폼이지만, 여전히 "Shopify Core"라는 단일 Ruby on Rails 애플리케이션(내부적으로는 도메인별로 잘 나뉜 "모듈러 모놀리스")으로 대부분의 기능을 서비스한다. Rails 모놀리스는 유지하면서 필요한 일부만 마이크로서비스로 감싸는 방식. GitHub도 저장소/PR 관리에 모듈러 모놀리스를 사용.
- **결론**: 신생 서비스는 대체로 모놀리식으로 시작하고, 규모가 커지고 조직이 나뉘면서 필요한 부분만 MSA로 전환하는 것이 훨씬 흔한 패턴 (Netflix, Amazon, Uber 모두 이런 경로를 거침).

## 2. 모놀리식 vs MSA — 구조 비교

### 요청 처리 흐름

**MSA**
```
클라이언트 → API 게이트웨이(단일 진입점) → 로드 밸런서
→ 로드 밸런서가 서비스 디스커버리에 인스턴스 위치 조회
→ 실제 서비스 인스턴스(예: 주문 서비스)로 라우팅
```

**모놀리식**
```
클라이언트 → 로드 밸런서 → 모놀리식 앱 인스턴스
  (내부에 회원·주문·결제 모듈이 함수 호출로 뭉쳐 있음)
```

모놀리식에는 **API 게이트웨이와 서비스 디스커버리 계층 자체가 없다.** 찾아야 할 서비스가 애초에 하나(이 앱)뿐이라, 로드 밸런서가 동일한 앱의 복제본들에 트래픽만 나눠주면 끝이기 때문이다.

### 배포/운영 흐름

**MSA**: 서비스별로 독립된 CI/CD 파이프라인 → 컨테이너 오케스트레이션이 서비스별 컨테이너를 배포·스케일링·복구 관리. 결제 로직 하나만 고쳐도 결제 서비스만 재배포.

**모놀리식**: 단일 CI/CD 파이프라인 → 앱 전체를 통째로 빌드·배포. 결제 로직 하나만 고쳐도 회원·주문·결제가 다 뭉쳐있는 앱 전체를 재배포해야 함 (OCP 관점에서 모놀리식이 수정/확장에 불리한 이유).

### 데이터 저장

**MSA**: 서비스마다 별도의 DB (Database per Service 패턴, 5장 참고)
**모놀리식**: 모든 모듈이 하나의 공유 DB 사용 → 여러 모듈에 걸친 작업도 하나의 DB 트랜잭션으로 묶을 수 있어 분산 트랜잭션 문제 자체가 없음

## 3. MSA 운영에 필요한 인프라 요소

### 모놀리식(Monolithic)
애플리케이션의 모든 기능이 **하나의 코드베이스, 하나의 배포 단위**로 묶여 있는 전통적인 아키텍처. MSA의 반대 개념.

### API 게이트웨이
모든 클라이언트 요청이 거치는 **단일 진입점**. 단순 라우팅뿐 아니라 여러 서비스가 반복 구현할 필요 없는 공통 기능(cross-cutting concern)을 한곳에 모아두는 역할을 한다.

- **인증/인가**: 토큰(JWT 등) 검증을 게이트웨이에서 먼저 처리 → 각 서비스가 인증 로직을 중복 구현할 필요 없음 (SRP와 연결: 서비스가 인증이라는 무관한 책임을 떠안지 않게 함)
- **속도 제한(Rate Limiting)**: 특정 클라이언트의 과도한 요청을 차단/지연 → 악의적 공격 방어 + 자원 보호
- **응답 집계(API Composition)**: 클라이언트가 여러 서비스를 각각 호출하지 않도록, 게이트웨이가 내부적으로 여러 서비스를 호출해 결과를 하나로 합쳐 반환
- **프로토콜 변환**: 외부는 REST/JSON, 내부는 gRPC 등 다른 프로토콜을 쓸 때 중간에서 변환
- **로깅/모니터링, 회로 차단(Circuit Breaking)**: 모든 트래픽이 거치므로 전체 로깅이 용이하고, 응답 없는 서비스로의 요청을 차단해 장애 전파를 막음

**게이트웨이 자체의 이중화(HA)**: 게이트웨이도 단일 장애점(SPOF)이 될 수 있으므로, 로드 밸런서 → 여러 개의 동일한 게이트웨이 인스턴스 구조를 앞단에 한 겹 더 둔다. 하나가 죽으면 로드 밸런서의 헬스체크가 이를 감지해 트래픽 목록에서 제외하고 나머지 인스턴스로만 분배 (액티브-액티브 구성 — 원래도 여러 인스턴스가 동시에 일하고 있었기 때문에 매끄럽게 이어짐). 단, 속도 제한 카운트 같은 **공유되어야 하는 상태**는 게이트웨이 자체 메모리가 아니라 Redis 같은 외부 저장소에 둬야 한다 (그래야 어느 인스턴스가 요청을 받든 같은 카운트를 보고, 게이트웨이가 상태 없는(stateless) 구조를 유지할 수 있음).

### 서비스 디스커버리
서비스 인스턴스가 트래픽에 따라 계속 늘었다 줄었다 하는 MSA 환경에서, **각 서비스가 자기 위치(IP/포트)를 레지스트리에 등록**하고, 다른 서비스는 이름으로 그 레지스트리에 물어봐서 실제 위치를 찾는 메커니즘. (대표 도구: Eureka, Consul, 쿠버네티스 내부 DNS)

### 로드 밸런싱
같은 서비스가 여러 인스턴스로 복제돼 있을 때, 들어오는 요청을 여러 인스턴스에 고르게 분산시키는 역할. (분배 방식 예: 라운드로빈, 최소 연결 방식)

### CI/CD 파이프라인
- **CI(지속적 통합)**: 코드를 올릴 때마다 자동으로 빌드·테스트
- **CD(지속적 배포)**: 테스트 통과한 코드를 자동으로 실제 서버에 배포

서비스 개수가 많은 MSA에서는 수동 빌드/배포가 사실상 불가능해 자동화가 필수.

### 컨테이너 오케스트레이션
수많은 컨테이너(Docker 등)의 배포, 스케일링, 장애 복구, 네트워킹을 자동으로 관리해주는 시스템. (대표 도구: Kubernetes)

## 4. 서비스별 DB는 어떻게 관리하나

### 왜 필요하고, 왜 비용이 늘어나는가

서비스마다 DB를 따로 두면 **총 저장 용량과 관리 오버헤드(백업, 커넥션 풀, 모니터링 등)가 늘어나는 건 사실**이다. 이는 MSA가 서비스를 잘게 쪼갠 대가로 치르는 진짜 비용이며, 카드에서 언급된 "네트워크 비용 증가"와 같은 계열이다. 다만:
- 개별 DB는 그만큼 작고 가벼워짐 (전체 데이터를 다 담은 거대한 DB보다 각각은 훨씬 단순)
- 클라우드 관리형 DB 서비스(RDS 등)를 쓰면 트래픽에 따라 자동으로 스케일 조정되어 실제 사용량만큼만 비용 발생

### Database per Service 패턴

**핵심 규칙: 다른 서비스가 내 DB에 직접 접근하는 것을 허용하지 않는다.**

```
❌ 주문 서비스가 결제 서비스의 DB에 직접 SQL 쿼리
✅ 주문 서비스가 결제 서비스의 API를 호출해 필요한 정보만 받음
```

이는 DIP(의존 역전 원칙)와 같은 이유다 — 만약 주문 서비스가 결제 DB의 테이블 구조를 직접 알고 쿼리를 짜면, 결제팀이 자기 DB 스키마를 바꾸고 싶어도 주문 서비스가 깨질까 봐 바꿀 수 없다. 각 서비스 팀이 자기 DB의 스키마·인덱스·마이그레이션을 완전히 독립적으로 관리하려면, 다른 팀이 그 DB 내부 구조에 의존하지 않아야 한다.

### 다른 서비스 데이터가 자주 필요할 때 — 이벤트 기반 동기화

매번 API를 호출하면 느리고 비용도 크므로, 실무에서는 **이벤트 기반 데이터 동기화**를 사용한다. 예: 결제 서비스가 "결제 완료" 이벤트를 발행(Kafka 등)하면, 주문 서비스가 이를 구독해 자기 DB에 "결제 상태" 필드만 복사해 저장. 매번 결제 서비스에 물어볼 필요 없이 자기 DB만 보고 즉시 응답 가능 — 대신 데이터가 여러 DB에 약간씩 중복 저장된다. **속도와 독립성을 위해 일부 중복을 감수하는 트레이드오프.**

## 5. 분산 트랜잭션 문제 (구체 예시)

주문 서비스와 결제 서비스가 각자 별도 DB를 가지면, "주문 생성 + 결제 처리"를 하나의 DB 트랜잭션으로 묶을 수 없다. 주문은 성공했는데 결제 호출이 중간에 실패하면?

- 모놀리식이었다면: 하나의 트랜잭션으로 그냥 롤백하면 끝
- MSA에서는: 이미 커밋된 "주문"을 되돌릴 별도의 설계가 필요 → **Saga 패턴**: 실패 시 보상 트랜잭션(compensating transaction)을 순차적으로 실행해 이전 단계들을 되돌림

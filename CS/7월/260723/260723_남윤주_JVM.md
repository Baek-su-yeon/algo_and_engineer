JVM
자바 가상 머신

## 배경
과거에는 프로그램을 운영체제와 CPU 환경에 맞게 각각 컴파일해야 했음.

Window, Linux, macOS 각 운영체제마다 프로그램을 다르게 컴파일.

같은 프로그램이라도 실행환경이 달라지면 해당 환경에 맞게 다시 만들어야 하는 불편함. 

>> Write Once, Run Anywhere
한 번 작성하면 어디서든 실행할 수 있다.
서로 다른 운영체제와 자바 프로그램 사이를 연결하는 역할을 하는 JVM!

## 개념
Java Virtual Machine
자바 프로그램을 실행하기 위한 가상의 실행환경. 

컴퓨터 전체를 가상화하는 VirtualBox 같은 가상머신이 아님!

자바 프로그램은 운영체제를 직접 상대하지 않고 JVM 위에서 실행됨. 

자바 프로그램 > JVM > 운영체제와 하드웨어 

JVM 덕분에 자바 프로그램은 어떤 운영체제에서든 동일한 형태로 실행됨

## 자바 코드 실행 과정

C나 C++은 소스 코드를 특정 운영체제와 CPU가 이해하는 기계어로 직접 컴파일함. 

자바는 소스 코드를 바로 기계어로 변환하지 않음! JVM을 거치기 때문에, JVM이 이해할 수 있는 중간 형태인 바이트코드로 변환함. 

바이트 코드는 .class 파일에 저장되고 각 운영체제에 설치된 JVM이 바이트 코드를 기계어로 변환해 실행함. 

>> JVM이 운영체제에 종속. 동일한 .class 파일을 여러 운영체제에서 실행할 수 있음. 

## 주요 역할
1. 바이트 코드 실행
JVM은 .class 파일에 저장된 바이트코드를 읽고 기계어로 변환해 실행함. 

두 가지 바이트코드 처리 방식
- 인터프리터: 바이트코드를 한 줄씩 해석하며 실행.
- JIT 컴파일러: 반복해서 실행되는 코드를 기계어로 변환해 실행 속도를 높임. 

2. 메모리 관리
프로그램 실행에 필요한 데이터를 메모리에 저장하고 관리.

두 가지 대표적인 메모리 영역
- Heap: 프로그램에서 생성한 객체가 저장되는 공간
- Stack: 메서드 호출 정보와 지역변수가 저장되는 공간

기본적으로 객체는 Heap에 저장되고 메서드 실행 정보는 Stack에 저장됨

(메서드는 호출된 역순으로 종료되므로 후입선출인 Stack에, 객체는 메서드가 끝난 뒤에도 계속 사용될 수 있으므로 Heap에)

3. 가비지 컬렉션
프로그램 실행하다 보면 더 이상 사용되지 않는 객체가 생김. 
가비지 컬렉터를 통해 더 이상 사용되지 않는 객체를 찾아 자동으로 메모리에서 제거. 

## 의의
- 플랫폼 독립성: 동일 자바 바이트코드를 여러 운영체제에서 실행할 수 있음.
- 자동 메모리 관리: 가비지 컬렉션으로 사용하지 않는 메모리를 자동으로 정리
- 실행 중 성능 최적화: JIT 컴파일러가 자주 실행되는 코드를 찾아 기계어로 변환하고 최적화
- 다양한 언어 생태계: Java, Kotlin, Scala 등 여러 언어가 JVM 생태계 활용

## 한계
- 프로그램 실행 위해 JVM 설치되어 있어야 함.
- JVM 실행하고 바이트코드 처리 과정 때문에 초기 실행 느릴 수 있음.
- 가비지 컬렉션 실행될 때 프로그램 일시 멈출 수 있음.
- 메모리를 JVM이 자동으로 관리해서 개발자가 세밀하게 제어하기 어려울 수 있음.
